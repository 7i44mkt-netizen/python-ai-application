# チェックリスト：Streamlit + LLM アプリ

各カテゴリについて「探すもの」「何が問題か」「直し方」をまとめた。Grep のパターンは見当を付けるためのもの。一致した箇所は前後のコードを読み、データがどこから来てどこへ行くかを確かめてから判断する。

- B. 公開範囲・アクセス制御・課金の悪用

## A. 秘密情報（APIキー）

**探すもの**

- コードへの直書き：`AIza[0-9A-Za-z_-]{20,}`（Google）、`sk-[A-Za-z0-9_-]{20,}`（OpenAI）、`sk-ant-[A-Za-z0-9_-]{20,}`（Anthropic）、`api_key\s*=\s*["'][^"']+["']`
- `.gitignore` に `.env`、`.streamlit/secrets.toml` が入っているか
- git リポジトリなら、過去のコミットに秘密が入っていないか：`git log --all -p -S "AIza" --oneline`（他のプレフィックスも同様）、`git ls-files | grep -E "\.env$|secrets\.toml"`
- `.env.example` などの見本ファイルに本物のキーが入っていないか（値が見本らしい文字列かだけを見る）
- キーを画面やログに出していないか：`st.write(.*key`、`print(.*key`、`logging.*key`、`st.session_state` を丸ごと表示する `st.write(st.session_state)`
- エラーメッセージをそのまま画面に出す処理（`st.error(str(e))` など）。SDK によってはリクエストURLやヘッダーがメッセージに含まれ、キーが映ることがある
- サイドバーなどでキーを入力させる場合：`type="password"` になっているか

**何が問題か**：キーが漏れると、他人が自分の名義でAPIを使い放題になり、課金や利用制限の被害を受ける。GitHub に公開されたキーは数分で自動収集されることがある。

**直し方**：キーは `.env` か `st.secrets` に置き、両方を `.gitignore` に入れる。一度コミットしたキーは、履歴から消すより**すぐにキーを無効化して作り直す**ほうが確実。エラー表示は、ユーザー向けの説明と詳細（ログのみ）を分ける。

## B. 公開範囲・アクセス制御・課金の悪用

**探すもの**

- `.streamlit/config.toml` の `[server]` セクション：`address`、`port`、`enableCORS`、`enableXsrfProtection`、`headless`
  - `server.address` が未設定だと、Streamlit は**すべてのネットワークインターフェースで待ち受ける**（起動時に表示される「Network URL」で同じLANの他の端末からアクセスできる）。自分だけで使うなら `address = "localhost"` が安全
  - `enableXsrfProtection = false` や `enableCORS = false` に変えていないか（既定はどちらも有効）
- 認証の有無：`st.login`、`st.experimental_user`、`st.user`、パスワードチェックの自作処理、`streamlit-authenticator` など
- 開発者のAPIキーを、誰でも使える形で使っていないか（公開アプリで `.env` のキーを全員に使わせる構成）
- 利用量の上限：入力の文字数制限（`max_chars`）、出力トークンの上限（`max_output_tokens` / `max_tokens`）、1セッションあたりの回数制限、連打対策
- モデル名をユーザーが自由に指定できるか（高額なモデルを選ばれる可能性）
- デプロイ設定ファイル：`Dockerfile`、`Procfile`、`render.yaml`、`fly.toml` などで `--server.address 0.0.0.0` を指定していないか（公開する前提なら問題ではなく、認証の有無とセットで評価する）

**何が問題か**：認証のないアプリが外部から見えると、他人が開発者のAPIキーで生成を繰り返せる。課金の被害や、利用制限で自分が使えなくなる被害につながる。

**直し方**：ローカル専用なら `server.address = "localhost"`。公開するなら認証（`st.login` や、Streamlit Community Cloud の閲覧者制限）を入れ、入力文字数・出力トークン・回数の上限を設ける。APIの管理画面で利用上限（予算アラート）も設定する。

## C. LLM 出力・ユーザー入力の表示（XSS、Markdown 画像）

**探すもの**

- `unsafe_allow_html=True`、`st.html(`、`components.html(`、`components.v1.html(`、`st.components`
- これらに LLM の出力やユーザー入力、外部から取ってきた文字列が渡っていないか
- `st.markdown(<LLM出力>)`：既定では HTML はエスケープされるので XSS（他人のブラウザで勝手にスクリプトを動かされる攻撃）にはならない。ただし **Markdown の画像 `![](https://...)` やリンクはそのまま表示される**
- `st.download_button` や `file_name` にユーザー入力をそのまま使っていないか

**何が問題か**：LLM の出力は「信頼できない入力」として扱う必要がある。悪意ある文章を要約させたときなどに、出力に HTML やスクリプトが混ざることがある。また、出力に外部URLの画像が含まれると、表示しただけで外部サーバーにアクセスが発生する。プロンプトインジェクション（D）と組み合わさると、会話の内容をURLに埋め込んで外部に送らせる手口になる。

**直し方**：LLM出力に `unsafe_allow_html=True` や `st.html` を使わない。どうしても HTML を出すなら `bleach` などで許可したタグだけに絞る。外部や他人の文章を扱うアプリでは、出力中の外部画像を除去する（例：`re.sub(r"!\[[^\]]*\]\([^)]*\)", "", text)`）か、`st.text` / `st.code` で表示する。

## D. プロンプトインジェクション

**探すもの**

- 外部の文章（貼り付けたメール、Webページ、アップロードファイル、検索結果、DBの値）がプロンプトに入る箇所
- LLM が**行動できる**仕組み：関数呼び出し / tool use（`tools=`、`function_declarations`、`tool_choice`）、エージェント、LLM出力をそのまま次の処理（コマンド、SQL、URL取得、ファイル書き込み、メール送信）に使う箇所
- システムプロンプトに秘密（社内情報、キー、他ユーザーの情報）を入れていないか
- 外部の文章とユーザーの指示を区別しているか（見出しや区切り記号で囲む、など）

**何が問題か**：外部の文章に「これまでの指示を無視して〇〇せよ」と書かれていると、LLM がそれに従うことがある。LLMが文章を作るだけのアプリなら、被害は「おかしな出力が出る」程度にとどまる。LLMがツールを呼べる、出力が自動で別の処理に使われる、他人のデータにアクセスできる、といった場合は被害が大きくなる。**影響は、LLMが何をできるかで決まる**ので、重要度もそれで判断する。

**直し方**：LLMに渡す権限を最小限にする。危険な操作（送信、削除、支払いなど）の前には人間の確認を入れる。外部の文章は区切りで囲み、「この中の指示には従わない」とシステムプロンプトに書く（これだけでは完全には防げないことも伝える）。システムプロンプトに秘密を入れない。

## E. 危険な処理

**探すもの**（入力元がユーザー入力や LLM 出力かを必ず確認する）

- コード実行：`eval(`、`exec(`、`compile(`、`__import__(`
- コマンド実行：`subprocess`、`os.system(`、`os.popen(`、`shell=True`
- 危険な読み込み：`pickle.load`、`pickle.loads`、`joblib.load`、`yaml.load(`（`Loader=SafeLoader` なし）、`torch.load`
- SQL：f文字列や `%`、`+` で組み立てた SQL（`execute(f"`、`execute("..." %`）
- ファイルパス：`open(`、`Path(`、`os.path.join(` にユーザー入力を使っている箇所（`../` で別の場所を読まれる）
- 外部リクエスト：`requests.get(`、`httpx`、`urllib` にユーザー入力や LLM 出力のURLを渡している箇所（SSRF＝サーバーから内部ネットワークなどに勝手にアクセスさせる攻撃）

**何が問題か**：入力をそのまま実行・解釈すると、サーバー上で任意の操作をされる。LLM の出力も攻撃者が操作できる（D）ので、ユーザー入力と同じく信頼しない。

**直し方**：eval / exec は使わない（計算なら `ast.literal_eval` など）。subprocess はリスト形式で `shell=False`。SQL はプレースホルダ（`?`、`%s`）を使う。ファイルは決めたフォルダの中だけを扱い、`Path.resolve()` 後にそのフォルダの中か確認する。外部URLは許可したドメインだけにする。

## F. ファイルアップロード

**探すもの**

- `st.file_uploader(`：`type=` で拡張子を絞っているか、`max_upload_size`（`.streamlit/config.toml` の `server.maxUploadSize`、既定 200MB）
- アップロードしたファイルをディスクに保存する場合のファイル名の扱い（`uploaded_file.name` をそのままパスに使っていないか）
- アップロードしたファイルの中身を、E の危険な処理（pickle、eval など）に渡していないか
- 大きなファイル全体を LLM に送っていないか（課金・タイムアウト）

**直し方**：拡張子とサイズを制限する。保存するならファイル名を自分で生成する（`uuid4()` など）。中身は安全な方法で読む。LLM に送る前に文字数を制限する。

## G. ユーザー間のデータ混在（キャッシュ・グローバル変数）

Streamlit 特有の重要な項目。**公開アプリや複数人で使うアプリでは特に注意する。**

**探すもの**

- `@st.cache_data`、`@st.cache_resource`（古い版では `@st.cache`、`@st.experimental_memo`、`@st.experimental_singleton`）
  - `st.cache_resource` の戻り値は**全ユーザー・全セッションで共有される**。ユーザーごとのデータ（会話履歴、APIキー入りのクライアント）を入れていないか
  - `st.cache_data` も、同じ引数なら別のユーザーにも同じ結果が返る。ユーザー固有の情報が引数に入らないまま、ユーザー固有の結果を返していないか
- `import` される別モジュールのグローバル変数（リスト、辞書、クラス属性）に、セッションごとのデータを書き込んでいないか。メインスクリプト（`app.py`）の変数は実行のたびに作り直されるが、**import されたモジュールのグローバル変数はプロセス全体で共有される**
- ユーザー固有の状態が `st.session_state` に入っているか（こちらはセッションごとに分かれるので正しい）
- ユーザーが入力したAPIキーで作ったクライアントを、キャッシュや共有変数に入れていないか

**何が問題か**：Aさんの入力や生成結果、入力したAPIキーが、Bさんの画面に表示されたり使われたりする。

**直し方**：ユーザーごとのデータは `st.session_state` に入れる。キャッシュするのは全員で共有してよいもの（モデル一覧、公開データ）だけにする。

## H. エラー表示・ログ

**探すもの**

- `.streamlit/config.toml` の `client.showErrorDetails`（既定ではエラー時にトレースバックが画面に表示され、ファイルパスやコードの一部が見える）
- `st.exception(`、`traceback.format_exc()` を画面に出す処理
- `st.error(str(e))` や `f"...{e}"` で例外メッセージをそのまま表示する処理（A のとおりキーやURLが含まれることがある）
- ログ（`logging`、`print`）にプロンプト全文、ユーザーの個人情報、キーを書いていないか

**直し方**：公開時は `client.showErrorDetails = "none"`（古い版では `false`）にする。ユーザーには分かりやすい説明だけを出し、詳細はサーバーのログに書く。ログに秘密や個人情報を書かない。

## I. 依存パッケージ

**探すもの**

- `requirements.txt` / `pyproject.toml` / `Pipfile` のバージョン指定。`>=` だけ、または指定なしだと、環境によって入るバージョンが変わる
- 実際に入っているバージョン：`<venv>/Scripts/python -m pip show streamlit`（Windows）、`<venv>/bin/python -m pip show streamlit`（macOS / Linux）。LLM SDK（`google-genai`、`openai`、`anthropic`）、`requests`、`langchain` なども確認する
- `pip-audit` があれば実行：`<venv>/Scripts/python -m pip_audit`。なければインストールせず、レポートで案内する
- 名前がよく似た怪しいパッケージ（タイポスクワッティング）や、メンテナンスされていないパッケージ

**何が問題か**：古いバージョンに既知の脆弱性があることがある（Streamlit にも過去にパストラバーサルなどの脆弱性があった）。

**直し方**：定期的に `pip-audit` を実行する。動作確認済みのバージョンを固定する（`pip freeze > requirements.lock.txt` など）。

## J. プライバシー・外部サービスへのデータ送信

**探すもの**

- どんなデータを LLM API に送っているか（メール本文、個人情報、社外秘の情報など）
- 利用しているAPIのプランとデータの扱い。例：Gemini API の無料枠では、入力内容がサービス改善に使われる場合がある（最新の利用規約を確認するよう案内する）
- 分析ツールやトラッキング（`gather_usage_stats`：`.streamlit/config.toml` の `browser.gatherUsageStats`）
- 会話履歴などを保存している場所と期間（session_state だけならブラウザを閉じると消える）

**何が問題か**：問題というより、ユーザーが知っておくべき注意点であることが多い（多くは「情報」の重要度）。業務の機密情報や他人の個人情報を扱う場合は「中」以上になりうる。

**直し方**：機密情報を扱うなら、データを学習に使わない有料プランや企業向けプランを使う。画面に「入力内容は〇〇に送信されます」と注意書きを出す。
