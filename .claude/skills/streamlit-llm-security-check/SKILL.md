# Streamlit + LLM アプリのセキュリティチェック

Streamlit で作った生成AIアプリを点検し、見つかった問題を**初心者にも分かる言葉で**レポートにまとめる。

このスキルの利用者は、個人開発やプロトタイプでアプリを作っている人が多い。セキュリティの専門家ではないので、「何が起きうるのか」「どう直せばいいのか」が具体的に分かることが一番大事。脅威の大げさな列挙より、そのアプリの実際の使われ方に合った、行動につながる指摘を優先する。

## 基本ルール

- **報告だけを行い、コードは変更しない。** 直し方はレポートにコード例として書く。ユーザーが後から「直して」と言った場合だけ修正する（その時点でこのスキルの範囲外）。
- **秘密情報の値を表示・転記しない。** `.env` や `secrets.toml` を確認するときは、キーの有無や形式だけを見る。レポートにも会話にも値を書かない（必要なら `AIza****` のように伏せる）。秘密がレポートに載ると、レポート自体が漏えい源になるため。
- **推測で断定しない。** コードを読んで確認できたことと、設定や運用次第で変わること（例：どこに公開するか）を区別して書く。

## 手順

### 1. アプリの全体像と使われ方をつかむ

まずプロジェクトのファイル構成、README、`requirements.txt`（または `pyproject.toml`）、`.gitignore`、`.streamlit/` フォルダを確認する。

次に**脅威モデル**（誰がこのアプリにアクセスでき、何を守りたいか）を決める。重要度の判断はこれで大きく変わる。

| 公開範囲 | 主なリスク |
|---|---|
| 自分のPCだけで使う | APIキーの漏えい（GitHubへの誤コミットなど）、依存パッケージ |
| 同じLAN内からアクセスできる | 上に加え、他人による無断利用（自分のAPIキーで課金される） |
| インターネットに公開（Streamlit Community Cloud など） | 上に加え、課金の悪用、ユーザー間のデータ混在、XSS、プロンプトインジェクション |

README や会話から公開範囲が分からなければ、ユーザーに一言確認する。答えがなければ「将来公開する可能性がある個人用ツール」と仮定し、その仮定をレポートに明記する。

### 2. チェック項目を順に確認する

`references/checklist.md` を読み、全カテゴリを確認する。各項目には、何を探すか（Grep のパターン）、何が問題か、どう直すかが書いてある。

- 検索するのはアプリ自身のコードだけにする。仮想環境（`.venv/`、`venv/`、`env/`）、`site-packages/`、`node_modules/`、`__pycache__/` は除外する（ライブラリのコードが大量に一致し、本当の問題が埋もれるため）。依存パッケージはカテゴリ I で別に確認する。
- Grep でパターンを探し、見つかった箇所は**必ず前後のコードを読んで**本当に問題か判断する。パターンに一致しただけでは指摘にしない（例：`unsafe_allow_html=True` でも、表示するのが固定の文字列なら問題ない）。
- データの流れを追う：**入力元**（ユーザー入力、アップロードファイル、URL、LLMの出力）が**危険な使い道**（HTML表示、eval、SQL、ファイルパス、外部リクエスト、別のLLM呼び出し）にどう届くか。
- チェックリストにない問題に気づいたら、それも報告する。チェックリストは最低限の目安。

依存パッケージの確認では、`pip-audit` が使える環境ならそれを実行する。インストールされていなければ勝手に入れず、インストールされているバージョン（`pip show <パッケージ>` など）を記録し、レポートで `pip-audit` の実行方法を案内する。

### 3. 重要度を付ける

脅威モデルを踏まえて、次の4段階で付ける。

- **高**：今の使い方のままで、秘密の漏えい・金銭的な被害・他人のデータの流出が現実的に起きうる。すぐ直すべき。
- **中**：公開範囲を広げたり、条件が重なったりすると被害が出る。公開前には直すべき。
- **低**：被害は小さいか起きにくいが、直しておくと安全性が上がる。
- **情報**：問題ではないが、知っておくとよいこと（良い点や、運用上の注意）。

同じ問題でも、ローカル専用なら「低」、インターネット公開なら「高」になりうる。重要度の理由を一言添える。

### 4. レポートを書く

プロジェクトのルートに `security_report.md` を作る（同名ファイルがあれば中身を確認し、上書きしてよいかユーザーに聞く）。形式は次のとおり。

```markdown
# セキュリティチェックレポート：<アプリ名>

- 実施日：YYYY-MM-DD
- 対象：<フォルダパス>（<確認したファイル一覧>）
- 想定した使われ方：<脅威モデル。仮定したなら「仮定」と明記>

## まとめ

<全体の評価を2〜4文で。最優先で直すべきことを1つ挙げる>

| 重要度 | 件数 |
|---|---|
| 高 | n |
| 中 | n |
| 低 | n |
| 情報 | n |

## 指摘一覧

| # | 重要度 | 内容 | 場所 |
|---|---|---|---|
| 1 | 高 | <一言で> | `app.py:42` |

## 指摘の詳細

### 1. <タイトル>（重要度：高）

- **場所**：`ファイル:行番号`
- **何が問題か**：<専門用語は短く説明しながら>
- **起きうること**：<具体的なシナリオ。「誰が・何をすると・どうなるか」>
- **直し方**：<手順と、必要ならコード例>
- **重要度の理由**：<脅威モデルとの関係>

## 問題がなかった項目

<確認して問題がなかったカテゴリを箇条書きで。何を確認したかが分かるようにする>

## 次にやるとよいこと

<優先順に3〜5個。ツールの導入（pip-audit など）や公開前の確認事項も含める>
```

書き方のポイント：

- 指摘は重要度の高い順に並べる。
- 「XSS」「SSRF」などの用語は、初出で一言説明する（例：「XSS（他人のブラウザで勝手にスクリプトを動かされる攻撃）」）。
- 「問題がなかった項目」も必ず書く。何を確認したかが分かると、レポートを信頼して使えるため。
- 直し方のコード例は、そのアプリのコードに合わせて書く（一般論のコピペにしない）。

### 5. 会話で結果を伝える

レポートのファイルパスと、まとめ（件数と最優先の指摘）を短く伝える。コードは変更していないことを明記し、修正したい指摘があれば番号で伝えてもらうよう案内する。
